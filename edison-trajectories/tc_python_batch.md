Question: What are the capabilities and limitations of Thermo-Calc's TC-Python API for high-throughput batch calculations? How does TC-Python handle parallelism, licensing for concurrent calculations, and integration with HPC schedulers like SLURM? Are there published examples of using TC-Python for screening thousands of alloy compositions in parallel?

## Capabilities and Limitations of Thermo-Calc's TC-Python API for High-Throughput Batch Calculations

### 1. Core Capabilities of TC-Python

TC-Python is Thermo-Calc's Python-based software development kit (SDK) that exposes most base Thermo-Calc features and makes the CALPHAD software fully scriptable, enabling loops, matrix operations, and post-processing within standard Python workflows (vary2023highthroughputstudyof pages 77-80). The API supports a broad range of calculation types including single-point and multi-point equilibrium calculations, Scheil–Gulliver solidification simulations, diffusion (DICTRA) simulations, precipitation (TC-PRISMA) simulations, property-model evaluations (phase fractions, compositions, liquidus/solidus temperatures, site occupancies), and computations of thermophysical properties such as coefficients of thermal expansion and molar volumes (sundar2025calphadbasedbayesianoptimization pages 8-9). TC-Python interacts with Thermo-Calc's suite of thermodynamic and kinetic databases (e.g., TCFE9, TCNI8, MOBNI4, TCHEA, TCNI12) and allows users to specify arbitrary temperature ranges and step sizes—for example, diffusivity data computed from 0 to 2000 °C with 1 °C resolution and Scheil profiles with 0.5 °C steps (sundar2025calphadbasedbayesianoptimization pages 8-9).

In addition to the TC-Python SDK, Thermo-Calc introduced a graphical "batch calculation mode" in version 2021b that accepts CSV/spreadsheet inputs of compositions and temperatures and executes predefined property-model equilibrium calculations row-by-row, handling "up to tens of thousands" of input rows (vary2023highthroughputstudyof pages 77-80). This batch mode serves as an alternative for users who lack SDK licenses.

### 2. Parallelism and Multiprocessing

TC-Python does not natively implement internal parallelism for distributing calculations across cores; rather, individual equilibrium calculations are executed sequentially within a single TC-Python session. To achieve parallelism, researchers combine TC-Python with Python's `multiprocessing` library to distribute independent calculations across multiple processor cores (sundar2025calphadbasedbayesianoptimization pages 8-9). Since each CALPHAD equilibrium calculation for a given composition and temperature is independent of others, these workloads are embarrassingly parallel and well-suited to process-level parallelism (kwon2024equilipyapython pages 5-7).

### 3. Licensing Constraints for Concurrent Calculations

A significant limitation of TC-Python for HPC-scale work is its licensing model. According to the Equilipy documentation, TC-Python permits only up to 32 logical processors per license, which can restrict scaling on HPC systems with many more available cores (kwon2024equilipyapython pages 1-3). The SDK itself requires a separate license from the base Thermo-Calc installation, and MATLAB-based SDK access requires an additional MATLAB license (vary2023highthroughputstudyof pages 77-80). This processor cap has been cited as a motivating factor for the development of open-source alternatives such as Equilipy, which aims to remove such constraints and operate freely on Linux-based HPC clusters (kwon2024equilipyapython pages 1-3, kwon2024equilipyapython pages 5-7).

### 4. Integration with HPC Schedulers (SLURM)

No published studies were identified that explicitly describe TC-Python integration with SLURM or other HPC job schedulers. In practice, researchers who use TC-Python on HPC systems appear to wrap the API within standard Python multiprocessing workflows that can be submitted as batch jobs to cluster schedulers (sundar2025calphadbasedbayesianoptimization pages 8-9). The 32-processor licensing limit per instance means that scaling beyond a single node typically requires either multiple licenses or an external distributed computing framework.

The most notable third-party solution for distributed CALPHAD execution is **Malac-Distmas** (Machine Learning Accelerated Distributed Task Management System), which implements a server–client architecture specifically designed for high-throughput CALPHAD workflows (gao2022amachinelearning pages 10-11, gao2022amachinelearning pages 3-5, gao2022amachinelearning pages 2-3). The server manages a SQL database of tasks (with status tracking: created, downloaded, executing, completed, or failed), distributes subtasks to client executors running on different compute nodes, handles exceptions and requeuing of failed jobs, and supports load balancing across heterogeneous resources (gao2022amachinelearning pages 3-5, gao2022amachinelearning pages 2-3). Malac-Distmas supports coupling with Thermo-Calc (via TCM batch files) and Pandat, and includes an embedded ANN module to "densify" calculation outputs and reduce the total number of explicit CALPHAD runs needed (gao2022amachinelearning pages 10-11, gao2022amachinelearning pages 9-10). This architecture could in principle be deployed behind SLURM or similar schedulers, though no published example of such deployment was found.

### 5. Known Limitations

Beyond licensing constraints, several practical limitations of TC-Python for high-throughput work have been documented:

- **Numerical instabilities**: Thermo-Calc's Newton–Raphson-based Gibbs energy minimization can drive searches to unreasonably high temperatures due to extrapolation artifacts, necessitating user-imposed maximum temperature limits (e.g., 2,500 K) to avoid nonphysical results (zhang2022identificationofthe pages 1-2).
- **Computation time**: Direct CALPHAD calculations are computationally expensive at scale. Computing equilibria for 150,000 unique compositions at five temperatures required approximately 11 days on a standard workstation (wang2025multiscalecomputationalframework pages 2-3). Not all calculations succeed; Sundar et al. reported a ~5% failure rate in data retrieval for ~2,000 compositions (sundar2025calphadbasedbayesianoptimization pages 8-9).
- **Combinatorial explosion**: The number of required calculations grows exponentially with the number of elements and compositional resolution, making exhaustive screening of high-order systems (quaternary and beyond) impractical without dimensionality reduction or surrogate strategies (zhang2022identificationofthe pages 1-2, ghassemali2022highthroughputcalphada pages 4-5, wang2020uncertaintyquantificationand pages 13-16).
- **Database dependence**: All CALPHAD predictions depend on the quality and coverage of the underlying thermodynamic databases, which limits accuracy for extrapolation to unexplored composition or temperature regimes (wang2020uncertaintyquantificationand pages 1-4, vary2023highthroughputstudyof pages 62-66).

Several landmark studies have demonstrated TC-Python and Thermo-Calc for screening thousands to hundreds of thousands of alloy compositions:

**Wang & Xiong (2020)** screened 450,000 HSLA-115 compositions using TC-Python with the TCFE9 database within a CALPHAD-based ICME framework, coupling equilibrium thermodynamic outputs with physics-based strengthening, weldability, and toughness models. Surrogate models enabled uncertainty quantification across the composition space, and the optimized composition raised the probability of successful additive manufacturing builds from 55.3% to 99.996% (wang2020uncertaintyquantificationand pages 10-13, wang2020uncertaintyquantificationand pages 1-4, wang2020uncertaintyquantificationand pages 7-10).

**Sundar et al. (2025)** used TC-Python (v2023b) with Python's multiprocessing library on HPC systems to compute phase diagrams, diffusivities, CTE, and Scheil profiles for ~2,000 Ni–Cr–Co–Al–Fe compositions within a Bayesian optimization framework, successfully retrieving data for 1,889 alloys and identifying Pareto-optimal candidates by exploring only 7% of the composition space (sundar2025calphadbasedbayesianoptimization pages 8-9).

**Vary (2023)** performed 65,568 point-equilibrium calculations across the Cr–Fe–Ni–Mo–Ti system using Thermo-Calc's batch calculation mode with two databases, demonstrating that the CSV-based batch interface can handle very large input files without requiring SDK licenses (vary2023highthroughputstudyof pages 77-80).

**Zhang et al. (2022)** implemented an in-house TC-Python loop to systematically screen the Al–Mg–Zn–Cu quaternary system for eutectic identification, demonstrating the workflow from binary through quaternary validation (zhang2022identificationofthe pages 1-2).

**Gao et al. (2022)** developed Malac-Distmas for distributed, fault-tolerant execution of CALPHAD calculations, demonstrating throughput of 10,201 diffusion tasks in 4.4 hours and 101 precipitation tasks in 24 minutes, with SQL-based storage and ANN-assisted data densification (gao2022amachinelearning pages 10-11, gao2022amachinelearning pages 3-5, gao2022amachinelearning pages 9-10).

### 7. Machine Learning Surrogates as a Scaling Strategy

Given the computational cost and licensing limitations of TC-Python, multiple groups have adopted machine learning surrogates trained on Thermo-Calc outputs to extend screening to much larger scales. Vazquez et al. (2023) trained a deep neural network on Thermo-Calc phase-fraction data for a seven-element HEA system, achieving R² > 0.96 and enabling screening of 500,000+ compositions and optimization runs requiring thousands of function calls in minutes rather than days (vazquez2023adeepneural pages 6-9, vazquez2023adeepneural pages 1-2). Wang et al. (2025) trained ML models on 750,000 CALPHAD datapoints to screen 2 billion Ni-based superalloy compositions, far exceeding what would be practical with direct TC-Python calls (wang2025multiscalecomputationalframework pages 2-3). These approaches highlight that TC-Python is best used for generating high-quality training data, while surrogate models handle the extreme-throughput screening (wang2023integratedcomputationalmaterials pages 32-38, li2021towardshighthroughputmicrostructure pages 1-3).

### Summary

TC-Python is a capable and widely used API for automating CALPHAD calculations at the scale of thousands to hundreds of thousands of compositions. Parallelism is achieved through Python's multiprocessing module rather than native TC-Python primitives, and licensing restricts concurrent usage to a maximum of 32 logical processors per license. No published examples of direct SLURM integration were identified, though the Malac-Distmas framework provides a distributed computing architecture that could serve a similar role. For screening beyond ~10⁵ compositions, the community has increasingly adopted ML surrogate models trained on TC-Python-generated data, enabling evaluation of millions to billions of candidates at a fraction of the computational cost.
