pKGFN is underperforming here for two reasons at once: the implementation is likely wrong in ways that specifically hurt partial evaluation, and this synthetic 6-node problem is unusually favorable to full-evaluation methods. The strongest code-level problem is in `bofn_pkgfn_demo.py:155-213`: intermediate-node candidates are sampled uniformly from `problem.parent_bounds[k]`, but for nodes 3 and 5 those boxes are much wider than the reachable parent-output region seen in `node_correlations.png` / `node_correlations.json`. For node 3, the plot shows `y1` is almost entirely positive, about 0.05–0.60, while `pkgfn_step` samples from `[-1,1]`; for node 5, only about 5.8% of the `[-2,2]×[-2,2]` box overlaps the empirical `(y3,y4)` range visible in the figure. That means many pKGFN partial evaluations are spent on out-of-distribution parent settings, so the downstream node GPs are updated in regions irrelevant to the optimization target. This is supported by the benchmark behavior: across 20 seeds and 881 pKGFN iterations, node 0 was selected 450 times (51.1%), node 3 258 times (29.3%), node 5 66 times (7.5%), node 2 only 24 times, node 1 only 3 times, and node 4 never once. Yet `node_correlations.json` shows `R²(y4,y5)=0.901`, `R²(y3,y5)=0.509`, and `R²(y0,y5)=0.087`. So pKGFN is spending most of its effort on the cheapest but least informative node and completely ignoring the most informative intermediate node.

There is also a likely latent node-4 bug in `bofn_pkgfn_demo.py:197-206`. Node 4 has both an active input and a parent (`active_input_indices[4]=[4]`, `parent_nodes[4]=[3]`, `node_dims[4]=2`). In `pkgfn_step`, it is treated as an intermediate node for candidate generation (`:165-176`), so `candidates` for node 4 are 2D points in `(x4,y3)` space. But if node 4 ever became best, the reconstruction block at `:197-206` would take the `len(active_idx) > 0` branch and try to write that 2D candidate into `x_full[0, active_idx]`, which has length 1. That mismatch should error. Consistent with instability, pKGFN had 80 `error_fallback` iterations out of 881 total, and those fallbacks consumed $9,600 of post-init cost across seeds, 37.3% of the total pKGFN campaign cost after initialization. That is not a small nuisance. It is enough to distort the cost-matched comparison by itself. I can’t identify the exact exception type from the saved JSON alone because stack traces were not recorded, but this code path is one concrete high-risk source.

I also think the inner KG optimization is underpowered. In `bofn_actions_benchmark.py:396-401`, pKGFN is called with only `n_fantasies=16` and in `bofn_pkgfn_demo.py:156` each node gets only `n_raw=32` random candidates. Then the best candidate is chosen by direct discrete evaluation at `:180-185`, with no gradient-based inner optimization. That is much cruder than the optimization strategy used in the Buathong et al. p-KGFN work. With 2D candidate spaces for nodes 3, 4, and 5, and only a small fraction of those boxes corresponding to reachable parent values, the effective number of relevant candidates is tiny. Using the empirical ranges visible in `node_correlations.png`, node 5 gets only about 2 relevant candidates on average out of 32. So yes: too few fantasies and a very weak inner optimizer are plausible contributors. But they are not the whole story. Even with more fantasies, the current candidate-generation scheme is still targeting the wrong regions.

On cost normalization, the code does divide by the per-node cost at `bofn_pkgfn_demo.py:190-191`, and the costs in the run config are consistent with the manuscript summary: `[5,10,10,45,20,30]`, total $120. So the normalization formula itself looks right. The issue is that with noisy KG estimates, dividing by cost strongly favors node 0. The observed selection pattern proves it: 51.1% of pKGFN steps went to node 0, which has almost no direct relation to `y5`. That is not what you’d want if the acquisition were estimating information gain on the final node well.

On the problem side, yes, this synthetic DAG does seem unusually favorable to HighFidOnly. The evidence is in `node_correlations.json` and the corresponding panels in `node_correlations.png`: `y0→y1` is strong (`R²=0.755`) and `y2→y3` is strong (`R²=0.766`), but `y1→y3` is weak (`R²=0.234`) and `y3→y4` is weak (`R²=0.210`), while `y4→y5` is almost linear (`R²=0.901`). That creates two weak information bottlenecks followed by a very easy terminal mapping. In plain terms, learning cheap upstream nodes does not reliably tell you about the final objective, but once you are near the end of the graph the final readout is almost trivial. That is exactly the regime where a vanilla GP on `y5` can do well, because direct full-pipeline observations bypass the weak links. The performance table is consistent with that: HighFidOnly reaches `1.150 ± 0.114`, statistically above pKGFN’s `1.043 ± 0.129`, while TSFN reaches `1.177 ± 0.062`. In paired tests over the 20 seeds, TSFN beat pKGFN by `Δ=0.134`, `t=3.626`, `p=0.0018`; HighFidOnly beat pKGFN by `Δ=0.106`, `t=2.741`, `p=0.0130`. By contrast, pKGFN was not distinguishable from Random in this sample (`Δ=0.043`, `t=1.017`, `p=0.322`). So this is not a subtle underperformance.

I do think that pattern is at least partly an artifact of the Matheron-path synthetic construction in `manufacturing_problem.py:202-229`. Node 5 is built deliberately smooth (`lengthscale=[[2.0,2.0]]`), node 4 is also fairly smooth (`[[1.5,1.0]]`), and both are sampled from tiny 5-point GP priors. That setup can easily create monotone, nearly linear downstream maps, which is exactly what the `y4` vs `y5` panel shows. If you want a more discriminating synthetic problem for BOFN, I’d change the generator so that the downstream links are nonlinear but still informative: shorter lengthscales on nodes 4 and 5, active inputs on node 5 or another competing terminal parent, and parent-child dependencies engineered to land in a moderate range instead of the current split between ~0.2 and 0.9. Right now the graph has “information dams” in the middle and an easy terminal readout, which is a weird combo for showcasing partial evaluation.

About the large standard deviations: they are real, but they look more like campaign instability than pure observation-noise explosion. All methods use `noise_std=0.05`, but TSFN’s final SD is only `0.062`, while pKGFN’s is `0.129` and LowFidOnly/Node2Only are about `0.162`. That points to algorithm sensitivity and poor information flow more than to unavoidable noise propagation. A useful diagnostic is that pKGFN’s final value is strongly tied to initialization quality: the Spearman correlation between initial best and final best was `ρ=0.600`, `p=0.005` for pKGFN, versus `ρ=0.380`, `p=0.098` for TSFN. So pKGFN is not robustly correcting a bad start. Another diagnostic is variance equality: Levene’s test comparing TSFN and pKGFN gave `F=11.706`, `p=0.0015`, so the higher pKGFN variance is statistically meaningful. I’d recommend four concrete checks next: first, log and inspect every pKGFN exception with stack traces and node IDs; second, save candidate locations and acquisition values per node per iteration so you can see whether node 0 is winning because of true KG or because of noisy estimates; third, compare the empirical reachable ranges of parent outputs against each `parent_bounds[k]`; fourth, rerun pKGFN with `n_fantasies` at 64 and `n_raw` at 128 or higher while keeping all seeds paired. For variance reduction in reporting, increase the posterior-mean tracking grid from 200 Sobol points to at least 512 and average that metric over several independent Sobol grids. The current 200-point tracker adds Monte Carlo noise on top of the BO variability.

On manuscript alignment: I cannot assess the stated FLAIME workflow in `main (2).pdf` because the file in the workspace is not a FLAIME manuscript. It is a VLM equipment-justification document, so I cannot quote or audit Activity 1 claims from it without the correct file. Based on the benchmark alone, though, I would soften any claim that pKGFN is reliably better than vanilla GP-EI in this regime. That is not supported by these data. A safer statement is that BOFN-style methods can help, but the benefit of partial evaluation is problem-dependent and implementation-sensitive. TSFN is the clean success case here; pKGFN is not. If you want an alternative algorithm to surface, I’d put TSFN first, then possibly an EI-style function-network method or a multi-task/multi-output GP on the full pipeline with node outputs as auxiliaries. Another reasonable direction is to treat partial pipeline prefixes as a true fidelity hierarchy rather than independent node probes, because the current implementation’s arbitrary parent-space probing is a bad match to the reachable-state geometry of this graph.

Most actionable fixes, in order: (1) repair node-4 handling in `bofn_pkgfn_demo.py:165-213`; (2) replace uniform parent-box candidate generation with candidates drawn from the empirical or posterior reachable parent manifold; (3) increase `n_fantasies` and candidate count substantially; (4) record and eliminate the `error_fallback` failures before making any methodological claims; (5) redesign the synthetic benchmark so downstream structure is nonlinear and intermediate nodes remain informative about the terminal objective.
